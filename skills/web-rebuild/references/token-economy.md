# Token Economy Without Quality Cuts

Load only for complex sessions, explicit budgets, or measurement. The entry point already contains the default rules. This guide is not a second always-on prompt or an instruction to change model settings.

## Spend Context Where It Changes the Decision

Start with the user's scope, repository instructions, native stack, affected route, and relevant components. Search for symbols and paths before opening large files. Read coherent surrounding blocks, not so little context that extra calls become necessary. Expand inspection when dependencies or uncertainty require it.

Use the stack table as an index; do not load every framework's details for one Laravel or React project. Read observation guidance when inspecting a reference, implementation guidance before code changes, and verification guidance when preparing captures. Skip references already understood and still applicable, not core design/security requirements.

For browser inspection, request the relevant region's computed styles, geometry, and interaction state rather than serializing the entire DOM repeatedly. Inspect enough of the page to preserve section order and responsive behavior. Keep original screenshots and logs as artifacts; surface only the meaningful deltas in conversation. Crops help local diagnosis but do not replace agreed full-page coverage or allow resizing comparison evidence.

## Reuse Work Safely

A previous observation is reusable only when source, code revision, viewport/DPR, assets/fonts, data, and interaction state are unchanged. Check for user/concurrent edits before applying a remembered patch. Rebuild or recapture when any relevant input changes. Never treat a summary or old screenshot as fresher evidence than the actual project.

For a long handoff, keep a short working checkpoint: mode/scope, stack/version, constraints, observed/inferred facts, files changed, commands/results, artifact paths and capture conditions, unresolved defects, next action. Exclude secrets and do not repeat full skill instructions. A checkpoint helps resume work; it does not authorize deleting host context or trusting stale assumptions.

## Build Less Unnecessary Code

Reuse an existing component if it can meet the required appearance and behavior. Native HTML/CSS controls are useful when equivalent; do not replace an observed custom picker with an incompatible native input just because it is shorter. Prefer installed tools to new infrastructure. Write focused custom code when it is the simplest correct way to meet the task.

Do not invent configuration, adapters for unrequested stacks, speculative caching, generalized factories, or a new design system for one screen. Do not generate several full implementations unless asked to compare alternatives. Reuse established tokens without forcing every distinct reference into the same template.

Minimal does not mean compressed identifiers, clever one-liners, missing error states, weakened escaping/CSRF, removed validation, or skipped accessibility. Follow the project's formatter and test conventions. Keep code editable and readable.

## Keep Verification Honest

During iteration, use targeted tests and captures for the affected area. After the final patch, run the agreed route/state/viewport matrix and applicable project regression checks. There is no universal one-test ceiling. Keep enough failure context to diagnose root causes; do not truncate away an error and call the command successful.

Stop when acceptance gates pass, the agreed correction budget is exhausted, or a real blocker prevents progress. Do not repeatedly rerun identical failing commands without a changed hypothesis. If time/token limits prevent required checks, report `partial` or `unverified` with the missing checks and ask for more budget when useful. Never silently lower thresholds or skip mobile to appear cheaper.

## Communicate Compactly

Default final format for a small change: what changed; checks actually run and outcomes; unresolved limitations; relevant paths. Link artifacts instead of dumping entire files or logs. Avoid repeated plans and ceremonial explanations. Expand when the user asks to learn, review, compare, or see full code. Compression applies to narration, not the product's content, translations, or useful UX copy.

Do not automatically install Ponytail or another skill, inject prompts into every subagent, add hooks, modify the host's reasoning budget, switch models, or weaken permissions. Those are separate user decisions and can add overhead rather than save it.

## Measure, Do Not Promise

Compare the same tasks/model/tool versions with and without this policy, preserving all quality gates and recording every run, not just successful cheap ones. Measure input/output/cached/reasoning tokens if the provider exposes them, image/tool context where reported, retries, wall time, cost, and completion quality. If usage is unavailable, report `not measured`; word count is not billed-token usage.

Short prompts can cause more retries, and extra rules themselves cost tokens. This project has not measured a savings percentage or demonstrated equal quality at lower cost. The evaluation cases are a plan, not results.

## Inspiration

[Ponytail by DietrichGebert](https://github.com/DietrichGebert/ponytail) distinguishes reducing unnecessary implementation work from merely shortening speech. Its source is MIT-licensed. This project's rules are independently written for reference-driven UI work; no Ponytail code, persona, hooks, or benchmark results are bundled. Its published savings do not establish savings for this package.
